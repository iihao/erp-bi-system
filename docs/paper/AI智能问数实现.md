# 5.X AI智能问数模块实现

## 一、系统架构概述

AI智能问数模块是本系统面向非技术用户提供自然语言数据查询能力的核心组件。用户通过自然语言提出问题（如"各楼盘的认购排行"、"本月各项目回款率趋势"），系统自动将自然语言转换为可执行的SQL查询语句，查询数据仓库后以表格、图表等形式返回结果。

系统的整体架构如**图5-X**所示（架构图），由四个核心模块构成：

（1）**语义检索与匹配**：对用户输入问题进行归一化处理、关键词提取和语义相似度计算，优先在标准SQL库和向量缓存中检索历史匹配结果。

（2）**AI在线生成**：当检索未命中时，调用大语言模型（通义千问系列）进行SQL在线生成，包含上下文理解、表结构选择、SQL生成和约束校验四个子步骤。

（3）**输出与应用**：将SQL查询结果转换为中文报表、字段明细表、趋势图表等多种可视化形式。

（4）**结果沉淀与反馈闭环**：通过人工确认、运维审核、结构化归档、知识沉淀形成标准问数资产池，持续迭代提升系统准确率。

## 二、语义检索与匹配层

### 1. 问题归一化处理

用户输入的自然语言问题往往包含礼貌用语、语气词和标点符号等噪声，直接影响关键词提取和相似度计算的准确性。系统实现了多层归一化处理：

```python
def normalize_question(question: str) -> str:
    # 去除礼貌用语前缀
    polite_words = ["请", "请问", "麻烦", "帮我", "你好"]
    for word in polite_words:
        if q.startswith(word):
            q = q[len(word):].strip()
    
    # 去除句末语气词和标点
    end_particles = ["呢", "吗", "吧", "啊"]
    q = q.rstrip("？?。！!,")
    
    return q.strip().lower()
```

归一化处理的目的是将"请问各楼盘的认购排行？"和"各楼盘的认购排行"映射为相同的规范化表示，提高缓存命中率和标准SQL库的匹配精度。

### 2. 关键词提取引擎

关键词提取是连接自然语言与数据库Schema的桥梁。系统内置了覆盖通用业务和地产领域的关键词词典，采用模式匹配的方式进行关键词识别。词典结构如下：

```python
keyword_patterns = {
    '销售': ['销售', '销售额', '销量', '成交', '签约额'],
    '回款': ['回款', '收款', '付款', 'payment', '款项'],
    '项目': ['项目', '楼盘', '地产', 're_projects'],
    '合同': ['合同', '签约', 'contract'],
    '成本': ['成本', '预算', '费用', 'cost', '支出'],
    '损益': ['损益', '利润表', 'roi', '回报率', '净利润'],
    '去化': ['去化', '去化率', '售罄'],
    '认购': ['认购', '认筹', 'subscription'],
    ...
}
```

关键词提取流程：遍历用户问题的所有子串，与词典中的模式进行匹配，匹配成功的模式对应的类别关键词被提取。若标准词典未命中，则通过正则表达式`[一-龥]{2,4}`提取2-4字中文词组作为候选关键词。

### 3. 标准SQL库匹配

标准SQL库是系统运维人员在长期使用过程中沉淀的SQL模板集合。每个标准SQL记录包含以下字段：

| 字段 | 说明 | 示例 |
|------|------|------|
| question_template | 问题模板 | "各楼盘认购排行" |
| keywords | 关联关键词 | ["项目", "认购", "排行"] |
| standard_sql | 标准SQL语句 | SELECT ... FROM dwd_trade_detail ... |
| explanation | 口径说明 | "按项目统计认购金额降序排列" |

匹配算法采用关键词重叠度评分机制：

```
score = Σ(关键词i ∈ 用户关键词 ∩ 标准SQL关键词)
      + (归一化问题完全匹配模板 ? 4 : 0)
      + Σ(关键词i ∈ 用户关键词 ∩ 模板文本)
```

评分最高的标准SQL记录被选中，系统直接返回其standard_sql，无需调用AI。这一机制的优势在于：

- **零延迟**：内存匹配仅需<1ms，无需网络请求
- **零成本**：不消耗大模型token配额
- **可审计**：所有SQL均经过运维审核，口径明确
- **可复用**：相同问题多次查询直接命中，保证结果一致性

### 4. 向量语义匹配

当标准SQL库未命中时，系统引入向量语义匹配作为二级缓存。该层利用文本Embedding模型（text-embedding-v4）将用户问题映射到1024维向量空间，通过余弦相似度计算与历史问数记录的匹配度。

向量匹配的核心逻辑：

```python
# 门控：相似度 >= 0.78 且与第二名间距 >= 0.04
if best_score >= 0.78 and (best_score - second_score) >= 0.04:
    return {
        "sql": best_match["sql_result"],
        "explanation": "向量语义匹配",
        "score": round(best_score, 3),
    }
```

门控机制包含双重约束：

（1）**绝对阈值**：余弦相似度必须达到0.78以上，确保语义层面的强关联。低于此阈值说明语义差异过大，不应复用的SQL。

（2）**相对间距**：最佳匹配与次佳匹配的间距必须大于0.04。这一设计防止了多个候选均较接近时的误匹配场景。例如，"各楼盘销售排行"与"各楼盘回款排行"的语义相似度可能均较高，但间距门控能确保只有最明确的匹配才被选中。

向量库采用内存+数据库双层存储架构：系统启动时从`query_vectors`表加载最近1000条向量记录到内存缓存，内存中执行O(n)余弦相似度计算；每次AI生成的新SQL在确认后通过`vector_store.save()`写入数据库并同步到内存缓存，形成自我演进的语义知识库。

## 三、AI在线生成层

当语义检索（标准SQL库 + 向量缓存）均未命中时，系统进入AI在线生成流程。该流程包含四个核心步骤。

### 1. 上下文理解

系统构建了覆盖59张数据库表的Schema上下文（DB_SCHEMA_CONTEXT），将表结构说明注入大语言模型的system prompt中。Schema上下文按业务模块分层组织：

- **地产销售模块**（re_开头）：10张核心业务表，涵盖项目、楼栋、房源、客户、认购、合同、回款、应收、退款、跟进
- **数据仓库事实表**（dws_开头）：2张聚合事实表
- **数据仓库明细表**（dwd_开头）：7张清洗后明细表
- **应用数据层**（ads_开头）：7张报表宽表
- **维度表**（dim_开头）：5张维度表
- **ODS原始表**（ods_开头）：10张原始表

Schema上下文采用精简格式描述每张表的字段名和含义，而非完整DDL。例如：

```
3. re_units (房源表)
   - unit_id: 房源 ID
   - building_id: 所属楼栋 ID
   - unit_code/name: 房源编码/名称
   - floor: 楼层
   - total_price/unit_price: 总价/单价
   - unit_status: 房源状态
```

### 2. 表结构选择

系统通过Prompt引导大模型优先选择合适层级的数据表。Prompt规则如下：

```
规则：
1. 仅输出 SELECT 语句
2. 优先使用 ads_ / dws_ 聚合表，其次 dwd_ / re_ / ods_ 明细表
3. 使用 SQLite 兼容语法，结果默认 LIMIT 10
4. 金额字段建议除以 10000 显示为万元
5. 涉及项目对比时按金额降序排列
```

"优先使用聚合表"的设计原则基于以下考虑：DWS和ADS层表已完成数据清洗、关联和聚合，查询效率高，且指标定义明确（如payment_rate、profit_margin等衍生指标已预计算）。仅在聚合表无法满足查询需求时（如需要房间级别的明细状态分析），才回退到DWD层或ODS层。

### 3. SQL生成

系统调用通义千问模型（qwen3.6-plus）进行SQL生成，关键参数配置如下：

| 参数 | 值 | 说明 |
|------|-----|------|
| model | qwen3.6-plus | 通义千问3.6 Plus模型 |
| temperature | 0.1 | 低温度保证输出稳定性和一致性 |
| max_tokens | 500 | SQL查询通常不需要长输出 |
| timeout | 120s | 连接超时+读取超时配置 |

模型返回的SQL经过清理处理：移除markdown代码块标记（```sql / ```）、去除首尾空白字符，然后进入约束校验环节。

### 4. 约束校验

系统在SQL执行前和配置层实施多重安全约束：

（1）**SQL类型限制**：配置中定义`allowed_types: ["SELECT"]`，仅允许SELECT查询，拒绝INSERT/UPDATE/DELETE/DROP等写操作。

（2）**敏感词检测**：配置`sensitive_words: "DROP, DELETE, TRUNCATE, GRANT, REVOKE"`，任何包含这些关键字的SQL均被拦截。

（3）**敏感表保护**：配置`sensitive_tables: ["users", "roles", "permissions", "system_logs"]`，防止AI生成查询用户权限等敏感表的SQL。

（4）**SQLite兼容语法**：Prompt明确要求使用SQLite兼容语法，确保生成的SQL在系统使用的SQLite环境中可执行。

（5）**结果数量限制**：Prompt自动添加`LIMIT 10`默认限制，防止大结果集查询拖慢系统响应。

## 四、输出与应用层

SQL执行成功后，系统根据查询结果的字段特征和数据量自动推荐图表类型：

```python
def recommend_chart(columns: list, data: list) -> str:
    # 单维度 + 单指标（≤10行） → 饼图
    if col_count == 2 and row_count <= 10:
        return 'pie'
    
    # 包含时间字段 → 折线图
    if any(time_kw in columns for time_kw in time_keywords):
        return 'line'
    
    # 多维度 + 指标（≤20行） → 柱状图
    if col_count >= 2 and row_count <= 20:
        return 'bar'
    
    # 数据量大 → 表格
    return 'table'
```

推荐逻辑基于字段语义识别：包含"year/month/date/年/月"的字段触发折线图推荐（时间序列趋势），单维度+单指标触发饼图推荐（占比分析），多字段触发柱状图推荐（对比分析）。

最终输出包含：SQL语句、字段说明、数据结果、推荐图表类型和完整的思考过程（thinking字段）。

## 五、结果沉淀与反馈闭环

系统设计了完整的知识沉淀闭环，将用户的一次性查询转化为可复用的标准化资产。闭环流程包含六个步骤：

### 1. 人工确认

用户查看AI生成的SQL和查询结果后，可对结果的正确性进行确认。确认操作将查询记录标记为已验证，作为纳入标准SQL库的候选。

### 2. 运维审核

运维人员在管理后台查看待审核的查询记录，检查SQL的正确性、性能和安全合规性。审核通过后，运维人员可为该记录配置关键词、问题模板和口径说明。

### 3. 结构化归档

审核通过的记录写入`standard_sql_library`表，形成结构化的标准SQL库。每条记录包含：question_template（问题模板）、keywords（关键词）、standard_sql（标准SQL）、explanation（口径说明）、usage_count（使用次数）。

### 4. 知识沉淀

系统启动时自动执行`load_standard_sql_cache()`将所有启用的标准SQL加载到内存缓存中，同时执行`vector_store.sync()`将query_vectors表中的向量记录同步到内存。标准SQL库和向量库在每次变更时自动刷新。

### 5. 标准问数资产池

随着系统使用时间的增长，标准SQL库不断积累，形成覆盖常见业务场景的问数资产池。资产池的规模可通过统计指标监控：

- 标准SQL总数（total）
- 启用的标准SQL数（active）
- 累计使用次数（usageCount）
- 节省的token数（tokenSaved = usageCount × 2000）

### 6. 持续迭代

系统提供标准SQL库的增删改查API（CRUD接口），运维人员可根据业务变化持续更新标准SQL库。删除操作采用软删除（is_active = 0），保留历史记录以便追溯。

## 六、性能优化策略

系统在设计和实现中采用了多项性能优化措施，确保AI问数模块在高并发场景下的稳定性和响应速度。

### 1. LRU查询缓存

系统内置LRU（Least Recently Used）缓存层，容量为200条记录，以归一化后的问题文本作为缓存键：

```python
class LRUCache:
    def get(self, key):
        if key in self._cache:
            self._cache.move_to_end(key)  # 命中则提升到最新
            return self._cache[key]
        return None
    
    def put(self, key, value):
        self._cache[key] = value
        if len(self._cache) > self._maxsize:
            self._cache.popitem(last=False)  # 淘汰最久未使用
```

缓存命中率为第一优先级的响应路径，命中时响应时间趋近于0ms，不消耗任何AI token。

### 2. 四层匹配策略

系统按优先级依次尝试四个匹配层：

```
缓存层（LRU） → 标准SQL库 → 向量语义匹配 → AI在线生成
     0ms            <1ms          ~200ms          ~5s
     免费           免费          Embedding成本   LLM调用成本
```

每一层未命中时才进入下一层，确保绝大多数常见查询在前两层即可完成响应。

### 3. Schema缓存

59张表的Schema上下文（约300行文本）在服务启动时一次性加载到全局变量`_schema_cache`中，避免每次请求重复读取。Schema缓存可通过`refresh_schema_cache()`手动刷新。

### 4. HTTP连接复用

使用`httpx.AsyncClient`建立持久化连接池（max_connections=10, max_keepalive_connections=5），避免每次AI调用时重复建立TCP连接和TLS握手。

## 七、技术实现要点

### 1. 三层匹配策略的互补性

标准SQL库和向量语义匹配在功能上存在互补关系：

- **标准SQL库**匹配的是关键词和问题模板，适用于精确的场景（如"各楼盘销售排行"、"本月回款趋势"）。匹配依据是关键词重叠度，不依赖语义理解。

- **向量语义匹配**利用Embedding的语义空间映射能力，适用于表述变体但语义相同的场景（如"各楼盘卖得怎么样"与"各楼盘销售排行"）。匹配依据是向量空间中的余弦相似度。

二者结合覆盖了从精确匹配到模糊语义匹配的全谱，在确保准确率的同时最大化缓存命中率。

### 2. 编码计划Key与标准Key的路由

系统支持两类DashScope API Key：编码计划专属Key（sk-sp-前缀）和标准DashScope Key（sk-前缀）。编码计划Key不支持Embedding API，系统通过`_is_coding_plan_key()`检测Key类型，自动路由到不同的API端点（coding.dashscope.aliyuncs.com vs dashscope.aliyuncs.com），并在向量功能不可用时自动降级为仅关键词匹配模式。

### 3. 日志与统计

所有AI问数查询均记录到`ai_query_logs`表，包含：用户问题、生成的SQL、关键词、token消耗量、执行时间、匹配来源（标准库命中/AI在线生成/向量匹配）、状态（success/failed）和错误信息。系统通过`/ai-query/logs/stats`接口提供实时统计：总查询数、成功数、失败数、平均执行时间、总token消耗量、标准SQL命中次数。
