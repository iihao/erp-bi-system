# 5.3.3 DWS、ADS层数据聚合与建模实现

## 一、DWS层（服务数据层）设计与实现

DWS层（Data Warehouse Summary，数据仓库汇总层）是数据仓库架构中承上启下的关键层次，位于DWD明细层之上、ADS应用层之下。该层以业务分析主题为核心，将DWD层的明细数据按照主题域进行轻度聚合，形成面向特定分析场景的事实表与维度表。本系统DWS层共设计了5张表，包括2张事实表（销售-回款事实表、成本-费用事实表）和3张维度表（项目维度表、时间维度表、科目维度表）。

### 1. 销售-回款事实表（dws_sales_payment_fact）

销售-回款事实表以房地产销售业务中的合同为主线，将合同销售数据与回款数据进行关联聚合，形成销售进度分析的核心数据模型。该表的设计遵循星型模型原则，以合同为粒度组织数据，同时保留项目和客户维度信息，支持从项目、合同、时间等多个维度进行销售分析。

**表结构设计如表5-X所示：**

| 字段名 | 类型 | 说明 |
|--------|------|------|
| project_guid | VARCHAR(64) | 项目GUID（外键关联项目维度） |
| project_name | NVARCHAR(128) | 项目名称（冗余字段，便于快速查询） |
| contract_guid | VARCHAR(64) | 合同GUID（业务主键） |
| customer_guid | VARCHAR(64) | 客户GUID（外键关联客户维度） |
| date_key | DATE | 签约日期键 |
| year / month / day | INT | 年/月/日层级字段 |
| contract_amount | DECIMAL(14,2) | 合同总金额 |
| payment_amount | DECIMAL(14,2) | 已回款金额 |
| payment_rate | DECIMAL(8,2) | 回款率（payment_amount/contract_amount） |
| contract_count | INT | 合同数量 |
| payment_count | INT | 回款笔数 |
| data_version | DATE | 数据版本标识 |
| dt | DATE | T+1增量分区字段 |

**聚合SQL实现：**

```sql
INSERT INTO dws_sales_payment_fact (
    project_guid, project_name, contract_guid, customer_guid,
    date_key, year, month, day,
    contract_amount, payment_amount, payment_rate,
    contract_count, payment_count, data_version, dt
)
SELECT
    d.project_guid,
    d.project_name,
    d.contract_guid,
    d.customer_guid,
    DATE(d.contract_sign_date) AS date_key,
    YEAR(d.contract_sign_date) AS year,
    MONTH(d.contract_sign_date) AS month,
    DAY(d.contract_sign_date) AS day,
    SUM(COALESCE(d.total_price, 0)) AS contract_amount,
    COALESCE(SUM(p.payment_amount), 0) AS payment_amount,
    CASE
        WHEN SUM(COALESCE(d.total_price, 0)) > 0
        THEN ROUND(COALESCE(SUM(p.payment_amount), 0) * 100.0 /
             SUM(COALESCE(d.total_price, 0)), 2)
        ELSE 0
    END AS payment_rate,
    COUNT(DISTINCT d.contract_guid) AS contract_count,
    COUNT(DISTINCT p.payment_guid) AS payment_count,
    CURDATE() AS data_version,
    %s AS dt
FROM dwd_trade_detail d
LEFT JOIN dwd_payment_detail p
    ON d.contract_guid = p.contract_guid AND p.dt = %s
WHERE d.dt = %s AND d.contract_guid IS NOT NULL
GROUP BY
    d.project_guid, d.project_name, d.contract_guid, d.customer_guid,
    DATE(d.contract_sign_date), YEAR(d.contract_sign_date),
    MONTH(d.contract_sign_date), DAY(d.contract_sign_date)
ON DUPLICATE KEY UPDATE
    payment_amount = VALUES(payment_amount),
    payment_rate = VALUES(payment_rate),
    payment_count = VALUES(payment_count),
    data_version = VALUES(data_version);
```

该聚合逻辑的核心设计要点包括：

（1）**LEFT JOIN关联策略**：以销售合同明细表（dwd_trade_detail）为主表，LEFT JOIN回款明细表（dwd_payment_detail）。采用左连接而非内连接的原因在于，部分新签约合同可能尚未产生回款记录，若使用内连接将导致这些合同数据丢失，影响销售进度的完整性分析。

（2）**回款率计算与除零保护**：回款率 = 已回款金额 / 合同总金额 × 100%，使用CASE WHEN进行除零保护，当合同金额为0时返回0而非抛出除零异常。

（3）**增量更新机制**：所有DWS表均包含dt分区字段，ETL执行时先按当天dt值进行聚合，利用ON DUPLICATE KEY UPDATE实现幂等性。同一数据日期的多次执行不会产生重复记录，后次执行覆盖前次结果，确保数据一致性。

（4）**聚合粒度**：按项目、合同、客户、签约日期四个维度组合进行聚合，既保留了合同级别的明细可追溯性，又实现了跨合同的项目维度汇总能力。

### 2. 成本-费用事实表（dws_sales_cost_fact）

成本-费用事实表服务于房地产企业的成本控制分析，将合同付款数据与总账实际发生额、预算数据进行三方关联，形成成本-费用-预算对比分析模型。

**表结构设计如表5-X所示：**

| 字段名 | 类型 | 说明 |
|--------|------|------|
| project_guid | VARCHAR(64) | 项目GUID |
| project_name | NVARCHAR(128) | 项目名称 |
| contract_guid | VARCHAR(64) | 合同GUID |
| account_number | VARCHAR(50) | 科目编码（如5001=开发成本，6601=销售费用） |
| account_name | VARCHAR(100) | 科目名称 |
| cost_center | VARCHAR(64) | 成本中心 |
| date_key | DATE | 过账日期键 |
| year / month / day | INT | 年/月/日层级字段 |
| contract_amount | DECIMAL(14,2) | 合同金额 |
| cost_amount | DECIMAL(14,2) | 成本金额（科目编码以5开头的账户） |
| fee_amount | DECIMAL(14,2) | 费用金额（科目编码以6开头的账户） |
| budget_amount | DECIMAL(14,2) | 预算金额 |
| budget_variance | DECIMAL(14,2) | 预算偏差（actual - budget） |
| variance_rate | DECIMAL(8,2) | 预算偏差率 |
| data_version / dt | DATE | 数据版本与分区字段 |

**聚合SQL实现：**

```sql
INSERT INTO dws_sales_cost_fact (...)
SELECT
    d.project_guid, d.project_name, d.contract_guid,
    COALESCE(g.account_number, 'UNKNOWN') AS account_number,
    COALESCE(g.account_name, '未知科目') AS account_name,
    COALESCE(g.cost_center, 'UNKNOWN') AS cost_center,
    COALESCE(g.posting_date, CURDATE()) AS date_key,
    YEAR(COALESCE(g.posting_date, CURDATE())) AS year,
    MONTH(COALESCE(g.posting_date, CURDATE())) AS month,
    DAY(COALESCE(g.posting_date, CURDATE())) AS day,
    COALESCE(SUM(d.total_price), 0) AS contract_amount,
    COALESCE(SUM(CASE
        WHEN g.account_number LIKE '5%' THEN g.local_amount
        ELSE 0 END), 0) AS cost_amount,
    COALESCE(SUM(CASE
        WHEN g.account_number LIKE '6%' THEN g.local_amount
        ELSE 0 END), 0) AS fee_amount,
    COALESCE(SUM(b.budget_amount), 0) AS budget_amount,
    COALESCE(SUM(g.local_amount), 0) - COALESCE(SUM(b.budget_amount), 0) AS budget_variance,
    CASE
        WHEN COALESCE(SUM(b.budget_amount), 0) > 0
        THEN ROUND((COALESCE(SUM(g.local_amount), 0) - COALESCE(SUM(b.budget_amount), 0))
             * 100.0 / SUM(b.budget_amount), 2)
        ELSE 0
    END AS variance_rate,
    CURDATE() AS data_version, %s AS dt
FROM dwd_trade_detail d
LEFT JOIN dwd_gl_actual_detail g
    ON d.project_guid = g.cost_center AND g.dt = %s
LEFT JOIN dwd_gl_budget_detail b
    ON g.account_number = b.account_number
    AND g.fiscal_year = b.fiscal_year AND b.dt = %s
WHERE d.dt = %s
GROUP BY ...
ON DUPLICATE KEY UPDATE ...;
```

该聚合逻辑的核心设计要点包括：

（1）**三表关联模型**：通过合同明细表 LEFT JOIN 总账实际明细表 LEFT JOIN 总账预算明细表，构建了"合同-实际-预算"三位一体的分析模型。关联键分别为项目GUID匹配成本中心、科目编码匹配、财年匹配。

（2）**科目编码前缀分类聚合**：基于中国企业会计准则的科目编码体系，以科目编码首字符区分成本与费用。科目编码以5开头（如5001开发成本、5401制造费用）归入cost_amount，以6开头（如6601销售费用、6602管理费用、6603财务费用）归入fee_amount。这一设计通过CASE WHEN + LIKE模式实现，在SQL层面完成了科目的自动分类，无需额外维护分类映射表。

（3）**预算偏差计算**：budget_variance = 实际发生额 - 预算金额，variance_rate = 预算偏差 / 预算金额 × 100%。正偏差表示超支，负偏差表示节约。

（4）**COALESCE空值处理**：对三表关联可能产生的NULL值，统一使用COALESCE函数转换为默认值0，确保聚合结果中不出现NULL，避免前端报表展示异常。

### 3. 维度表构建

#### （1）项目维度表（dim_project）

项目维度表从ODS层的房间信息表（ods_room）中提取项目维度信息，采用SELECT DISTINCT去重后插入。维度属性包括项目GUID、编码、名称、城市、区域、产品业态、楼栋类型、建筑面积、总户数、开发商、物业等。该表使用ON DUPLICATE KEY UPDATE实现SCD Type 1（缓慢变化维类型1）策略，当项目信息发生变化时直接覆盖旧值。

```sql
INSERT INTO dim_project (...)
SELECT DISTINCT
    r.project_guid,
    CONCAT('PRJ_', r.project_guid) AS project_code,
    COALESCE(r.project_name, '未知项目') AS project_name,
    ...
FROM ods_room r
WHERE r.project_guid IS NOT NULL AND r.dt = %s
ON DUPLICATE KEY UPDATE
    project_name = VALUES(project_name),
    project_status = VALUES(project_status),
    dt = VALUES(dt);
```

#### （2）时间维度表（dim_date）

时间维度表是数据仓库中最基础的维度表，预生成2020年至2030年共11年的日期维度数据，总计约4018条记录。该表包含16个字段，覆盖年、季度、月、日、周、星期、节假日、财务年度等多层级时间层级。

时间维度的生成采用两种方式：首选方案通过MySQL存储过程（sp_init_dim_date）在数据库层面循环生成，利用MySQL内置的日期函数（YEAR、QUARTER、MONTH、WEEKDAY、WEEK等）计算各层级字段；备选方案通过Python的datetime库生成后批量INSERT，用于存储过程不可用的场景（如SQLite环境）。

```python
# Python备选方案核心逻辑
start_date = date(2020, 1, 1)
end_date = date(2030, 12, 31)
current_date = start_date
while current_date <= end_date:
    weekday = current_date.weekday()
    is_weekend = 1 if weekday >= 5 else 0
    is_holiday = 1 if (current_date.month == 1 and current_date.day == 1) else 0
    values.append((current_date, current_date.year,
                   (current_date.month - 1) // 3 + 1, ...))
    current_date += timedelta(days=1)
cursor.executemany(insert_sql, values)
```

#### （3）科目维度表（dim_account）

科目维度表从ODS层的科目表（ods_account）中提取，构建了包含17个标准会计科目的科目树。科目编码遵循中国企业会计准则体系：1001库存现金、1002银行存款、1122应收账款、1403原材料、4001主营业务收入、5001开发成本、6601销售费用、6602管理费用、6603财务费用等。该表维护了父子层级关系（parent_account_guid、level、is_leaf），支持科目树的前序遍历展示。

## 二、ADS层（应用数据层）设计与实现

ADS层（Application Data Service Layer，应用数据服务层）是数据仓库体系中最接近业务应用的一层，直接面向报表展示、数据分析和决策支持。该层根据具体报表需求，将DWS层的主题数据进行二次聚合和指标计算，生成可直接用于前端展示的宽表数据。本系统共设计了7张ADS层报表，覆盖销售分析、成本管理、财务分析和综合大屏展示四大业务场景。

### 1. 集团销售目标达成报表（ads_group_sales_report）

该报表服务于集团管理层对各项目销售目标完成情况的跟踪分析。数据来源于dws_sales_payment_fact事实表，按项目维度进行二次聚合，汇总各项目的合同金额作为实际完成值。

```sql
INSERT INTO ads_group_sales_report (...)
SELECT
    CURDATE() AS report_date,
    YEAR(CURDATE()) AS year, MONTH(CURDATE()) AS month,
    f.project_guid, f.project_name,
    0 AS target_amount,  -- 目标值需另行配置
    SUM(COALESCE(f.contract_amount, 0)) AS actual_amount,
    ...
FROM dws_sales_payment_fact f
WHERE f.dt = %s
GROUP BY f.project_guid, f.project_name;
```

该表预留了target_amount（目标金额）字段，支持后续通过目标配置表接入年度销售计划数据，实现目标达成率 = 实际金额 / 目标金额 × 100%的完整计算。

### 2. 集团签约回款周月年报（ads_group_salesdate_report）

该报表按日/周/月/年四个时间粒度，提供集团层面的签约与回款趋势分析。报表核心字段包括contract_amount（签约金额）、payment_amount（回款金额）、payment_rate（回款率）。

```sql
-- 日报生成
INSERT INTO ads_group_salesdate_report (...)
SELECT
    'daily' AS report_type,
    YEAR(f.date_key) AS report_year,
    WEEK(f.date_key) AS report_week,
    MONTH(f.date_key) AS report_month,
    f.project_guid, f.project_name,
    SUM(COALESCE(f.contract_amount, 0)) AS contract_amount,
    SUM(COALESCE(f.payment_amount, 0)) AS payment_amount,
    COALESCE(AVG(f.payment_rate), 0) AS payment_rate,
    ...
FROM dws_sales_payment_fact f
WHERE f.dt = %s AND f.date_key = CURDATE()
GROUP BY YEAR(f.date_key), WEEK(f.date_key), MONTH(f.date_key),
         f.project_guid, f.project_name;
```

报表类型（report_type）字段区分daily/weekly/monthly/yearly四种粒度，通过调度系统在不同时间点执行对应的聚合任务。当前版本已实现日报的自动生成，周报、月报、年报的生成逻辑与日报类似，仅GROUP BY的时间粒度不同。

### 3. 集团费用支出汇总报表（ads_group_pay_report）

该报表面向高层决策支持，将各项目维度的合同支出、费用支出进行汇总，形成集团层面的费用全景视图。数据来源于dws_sales_cost_fact事实表，按项目维度聚合。

```sql
INSERT INTO ads_group_pay_report (...)
SELECT
    CURDATE() AS report_date,
    f.project_guid, f.project_name,
    SUM(COALESCE(f.cost_amount, 0)) AS contract_pay_amount,
    SUM(COALESCE(f.fee_amount, 0)) AS fee_amount,
    SUM(COALESCE(f.cost_amount, 0)) + SUM(COALESCE(f.fee_amount, 0)) AS total_amount,
    SUM(COALESCE(f.budget_amount, 0)) AS budget_amount,
    SUM(COALESCE(f.budget_variance, 0)) AS variance_amount,
    COALESCE(AVG(f.variance_rate), 0) AS variance_rate,
    ...
FROM dws_sales_cost_fact f
WHERE f.dt = %s
GROUP BY f.project_guid, f.project_name;
```

关键指标设计：contract_pay_amount反映项目合同付款总额，fee_amount反映期间费用（管理费用、销售费用、财务费用）总额，total_amount为二者之和，variance_rate反映预算执行情况。

### 4. 项目成本费用报表（ads_project_cost_report）

该报表提供项目-科目两个维度的成本费用明细分析，是成本控制的核心报表。数据来源于dws_sales_cost_fact，按项目和科目维度二次聚合。

```sql
INSERT INTO ads_project_cost_report (...)
SELECT
    f.project_guid, f.project_name,
    f.account_number, f.account_name,
    CASE
        WHEN f.account_number LIKE '5%' THEN '成本'
        WHEN f.account_number LIKE '6%' THEN '费用'
        ELSE '其他'
    END AS cost_type,
    SUM(COALESCE(f.budget_amount, 0)) AS budget_amount,
    SUM(COALESCE(f.cost_amount, 0)) + SUM(COALESCE(f.fee_amount, 0)) AS actual_amount,
    SUM(COALESCE(f.budget_variance, 0)) AS variance_amount,
    CASE
        WHEN SUM(COALESCE(f.budget_amount, 0)) > 0
        THEN ROUND((SUM(COALESCE(f.cost_amount, 0)) + SUM(COALESCE(f.fee_amount, 0)))
             * 100.0 / SUM(f.budget_amount), 2)
        ELSE 0
    END AS completion_rate,
    ...
FROM dws_sales_cost_fact f
WHERE f.dt = %s
GROUP BY f.project_guid, f.project_name, f.account_number, f.account_name;
```

该表的特色在于cost_type字段，在ADS层再次执行科目编码前缀分类，将科目归入"成本"或"费用"类别。completion_rate（预算执行率）= 实际发生额 / 预算金额 × 100%，用于跟踪项目预算的执行进度。

### 5. 营销驾驶舱大屏（ads_sales_dashboard）

营销驾驶舱大屏数据为高层管理可视化提供核心指标。与前六张报表不同，该表的数据源并非DWS层事实表，而是直接聚合DWD层的房间明细表（dwd_room_detail），这是因为房间状态分析（可售/已售/已交付）需要房间级别的明细数据支撑。

```sql
INSERT INTO ads_sales_dashboard (...)
SELECT
    CURDATE() AS dashboard_date,
    d.project_guid, d.project_name,
    COUNT(DISTINCT d.room_key) AS total_units,
    SUM(CASE WHEN d.room_status IN ('signed', 'delivered', '已售')
        THEN 1 ELSE 0 END) AS sold_units,
    SUM(CASE WHEN d.room_status IN ('available', '可售')
        THEN 1 ELSE 0 END) AS available_units,
    ROUND(
        SUM(CASE WHEN d.room_status IN ('signed', 'delivered', '已售')
            THEN 1 ELSE 0 END) * 100.0 /
        NULLIF(COUNT(DISTINCT d.room_key), 0), 2
    ) AS sell_through_rate,
    SUM(COALESCE(d.total_price, 0)) AS total_sales,
    ...
FROM dwd_room_detail d
WHERE d.dt = %s
GROUP BY d.project_guid, d.project_name;
```

核心指标包括：total_units（总房源数）、sold_units（已售房源数）、available_units（可售房源数）、sell_through_rate（去化率，使用NULLIF防止除零异常）、total_sales（总销售额）、total_payment（总回款额，通过子查询从回款明细表获取）、avg_unit_price（平均单价）。

### 6. 财务驾驶舱大屏（ads_finance_dashboard）

财务驾驶舱大屏聚焦企业财务KPI指标，数据来源于总账实际明细表（dwd_gl_actual_detail），通过科目编码前缀识别收入类科目和成本费用类科目。

```sql
INSERT INTO ads_finance_dashboard (...)
SELECT
    COALESCE(g.company_code, 'UNKNOWN') AS company_code,
    SUM(CASE WHEN g.account_number LIKE '4%'
        THEN COALESCE(g.local_amount, 0) ELSE 0 END) AS total_revenue,
    SUM(CASE WHEN g.account_number LIKE '5%'
        THEN COALESCE(g.local_amount, 0) ELSE 0 END) AS total_cost,
    SUM(CASE WHEN g.account_number LIKE '4%'
        THEN COALESCE(g.local_amount, 0)
        WHEN g.account_number LIKE '5%'
        THEN -COALESCE(g.local_amount, 0) ELSE 0 END) AS total_profit,
    CASE
        WHEN SUM(CASE WHEN g.account_number LIKE '4%'
            THEN g.local_amount ELSE 0 END) > 0
        THEN ROUND(SUM(...) * 100.0 / SUM(...), 2)
        ELSE 0
    END AS profit_margin,
    ...
FROM dwd_gl_actual_detail g
LEFT JOIN dws_sales_cost_fact f ON g.cost_center = f.cost_center
WHERE g.dt = %s
GROUP BY g.company_code;
```

科目编码分类规则：4开头为收入类科目（如4001主营业务收入），5开头为成本类科目。利润总额 = 收入 - 成本，利润率 = 利润 / 收入 × 100%。

### 7. 收支利大屏（ads_szl_dashboard）

收支利大屏是综合性最强的展示模块，将销售收入、成本费用、利润三个维度的数据整合在一个分析视图中，服务于企业经营管理层的全局决策。数据来源于dws_sales_cost_fact事实表，按项目维度聚合。

```sql
INSERT INTO ads_szl_dashboard (...)
SELECT
    f.project_guid, f.project_name,
    SUM(COALESCE(f.contract_amount, 0)) AS sales_revenue,
    SUM(COALESCE(f.cost_amount, 0)) AS total_cost,
    SUM(COALESCE(f.fee_amount, 0)) AS total_expense,
    SUM(COALESCE(f.contract_amount, 0)) -
        SUM(COALESCE(f.cost_amount, 0)) -
        SUM(COALESCE(f.fee_amount, 0)) AS operating_profit,
    ...
    CASE WHEN SUM(COALESCE(f.contract_amount, 0)) > 0
        THEN ROUND((SUM(...) - SUM(...) - SUM(...))
             * 100.0 / SUM(f.contract_amount), 2)
        ELSE 0
    END AS profit_margin,
    CASE WHEN SUM(COALESCE(f.cost_amount, 0)) > 0
        THEN ROUND((SUM(...) - SUM(...) - SUM(...))
             * 100.0 / SUM(f.cost_amount), 2)
        ELSE 0
    END AS roi,
    ...
FROM dws_sales_cost_fact f
WHERE f.dt = %s
GROUP BY f.project_guid, f.project_name;
```

核心指标体系：sales_revenue（销售收入）取自合同金额，total_cost（成本总额）取自科目编码5开头的实际发生额，total_expense（费用总额）取自科目编码6开头的实际发生额，operating_profit（营业利润）= 收入 - 成本 - 费用，profit_margin（利润率）= 利润 / 收入 × 100%，roi（投资回报率）= 利润 / 成本 × 100%。

## 三、DWS与ADS层建模的关键技术要点

### 1. 星型模型与维度建模

本系统DWS层严格遵循Kimball维度建模方法论，采用星型模型（Star Schema）组织数据。星型模型由一个事实表（Fact Table）和围绕它的多个维度表（Dimension Table）组成。事实表存储度量值（如金额、数量），通过外键关联维度表。

本系统的两个主题域分别构建了独立的星型模型：
- **销售主题**：dws_sales_payment_fact为中心事实表，关联dim_date（时间维度）、dim_project（项目维度）
- **成本主题**：dws_sales_cost_fact为中心事实表，关联dim_date（时间维度）、dim_project（项目维度）、dim_account（科目维度）

### 2. 缓慢变化维（SCD）处理

维度表中的项目信息、科目信息等可能随时间发生变化。本系统对维度表采用SCD Type 1策略，即新值直接覆盖旧值（通过ON DUPLICATE KEY UPDATE实现）。这一策略的选择基于以下考虑：房地产项目维度的变化频率较低，且业务分析更关注当前最新的项目状态，历史状态的追溯需求较弱。对于有明确历史追溯需求的场景（如项目状态变更历史），可通过ODS层原始表查询实现。

### 3. T+1增量加载机制

所有DWS和ADS表均包含dt（date partition）日期分区字段，ETL调度执行时传入当天日期作为分区值。聚合SQL通过WHERE dt = %s限定源数据的分区范围，仅处理当天的数据，避免全表扫描。写入时通过ON DUPLICATE KEY UPDATE实现幂等性，确保同一天的多次执行不会产生重复数据。

### 4. 数据质量保障

在聚合过程中采用了多重数据质量保护措施：COALESCE函数将NULL值替换为0或默认字符串，防止空值导致聚合结果异常；NULLIF函数在除法运算中将零除数转换为NULL，避免MySQL的除零错误；CASE WHEN语句对边界条件（如金额为零时的比率计算）进行保护性处理。

### 5. 跨层数据血缘

本系统各层之间的数据血缘关系清晰可追溯：ODS层（9张原始表）→ DWD层（7张清洗后明细表）→ DWS层（2张事实表 + 3张维度表）→ ADS层（7张报表宽表）。每一层的数据仅从直接上层获取，不存在跨层引用，确保数据流向的单向性和可审计性。前端的数据血缘展示模块（DataLineage.vue）通过解析各表的INSERT ... SELECT语句中的源表引用关系，自动生成可视化血缘图谱。
