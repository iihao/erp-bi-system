# 5.6 AI 智能问数模块实现（优化稿）

## 5.6.1 模块目标与业务定位
在前述报表可视化与 RPA 自动化能力基础上，系统进一步引入 AI 智能问数模块，实现“自然语言提问—SQL 自动生成—结果可视化解读”的闭环能力。该模块主要面向管理层和分析人员的即席分析场景，解决传统报表“口径固定、响应慢、临时分析依赖技术人员”的问题。

结合本项目实现，AI 问数模块具备以下三类能力：
1. 自然语言转查询：用户通过自然语言输入业务问题，系统自动生成可执行 SQL。
2. 查询结果可视化：对结果集自动渲染柱状图、折线图、饼图，并支持图形切换。
3. 智能结果解读：对结果进行统计汇总并生成自然语言解读文本，降低管理层读表门槛。

## 5.6.2 模块架构与实现分层
本系统 AI 问数采用“前端交互层 + 服务编排层 + 安全治理层 + 日志分析层”四层实现。

1. 前端交互层（Portal）
前台页面提供问题输入、快捷问题、结果表格、图表展示、SQL 复制、数据导出等能力。用户请求通过统一鉴权 token 调用 AI 问数接口。

2. 服务编排层（API）
后端以 FastAPI 实现问数编排。核心流程为：问题接收、关键词提取、标准 SQL 库匹配、AI 生成 SQL（未命中时）、SQL 执行、结果返回。

3. 安全治理层（Guardrail）
系统在执行前后均执行安全校验，包含：敏感词过滤、危险 SQL 操作拦截、敏感表访问限制、只读查询约束（SELECT）。

4. 日志分析层（Audit）
系统记录问数日志，支持后台查询记录检索、成功率统计、趋势分析，并用于后续标准 SQL 库优化与提示词优化。

## 5.6.3 核心流程设计
本模块查询执行流程如下：
1. 用户输入自然语言问题（如“上个月销售额最高的产品是什么？”）。
2. 系统校验用户 AI 开关与当日配额（`ai_enabled`、`ai_quota`、`ai_used_today`）。
3. 系统进行敏感内容检测（敏感词、危险语句、敏感表）。
4. 提取问题关键词并优先匹配标准 SQL 库（`standard_sql_library`）。
5. 若未命中标准 SQL，则调用大模型接口生成 SQL；并进行 MySQL 到 SQLite 兼容转换（函数级转换）。
6. 再次执行 SQL 安全校验，通过后执行查询并返回数据集。
7. 写入问数日志（成功/失败、耗时、结果行数、错误信息），并更新用户当日已用次数。

该流程实现了“规则优先、模型兜底”的混合策略，可有效降低 token 消耗并提升常见问题响应稳定性。

## 5.6.4 数据模型与存储设计
### （1）用户 AI 权限字段扩展
在用户表扩展 AI 相关字段：
- `ai_enabled`：是否启用 AI 问数。
- `ai_quota`：用户每日问数配额。
- `ai_used_today`：用户当日已用次数。

该设计实现“按用户精细化限流与授权”。

### （2）问数日志表
系统通过 `ai_query_logs` 记录问数过程关键信息，用于审计和运维分析。核心字段包括：问题文本、生成 SQL、执行状态、执行耗时、结果行数、错误信息、创建时间等。

### （3）标准 SQL 库
系统维护 `standard_sql_library` 表，包含关键词、问题模板、标准 SQL、解释、使用次数、启用状态等字段。查询时优先命中标准 SQL，可降低模型调用频率并提升可控性。

## 5.6.5 接口设计与功能划分
系统将 AI 问数接口拆分为前台执行接口与后台治理接口。

1. 前台接口（用户侧）
- `POST /api/portal/ai-query/execute`：执行问数。
- `GET /api/portal/ai-query/quota`：查询配额。
- `GET /api/portal/ai-query/history`：查询个人历史。

2. 后台接口（管理侧）
- `GET /api/admin/ai-query/records`：问数记录分页检索。
- `GET /api/admin/ai-query/stats`：总量、成功量、失败量、成功率统计。
- `GET /api/admin/ai-query/trend`：按天趋势分析。
- `GET/POST/PUT/DELETE /api/admin/standard-sql`：标准 SQL 库管理。
- `GET/POST /api/admin/ai-config/*`：模型、提示词、权限、表结构映射等配置。

通过前后台分离，系统同时满足“业务用户便捷问数”和“管理员可治理、可审计”的双重要求。

## 5.6.6 前端可视化与智能解读实现
前端在问数结果页采用“解读 + SQL + 图表 + 表格”四段式展示：
1. 智能解读：基于结果集自动计算总计、均值、最大值、最小值并生成描述文本。
2. SQL 展示：展示并支持复制生成 SQL，增强可解释性。
3. 图表展示：基于结果前两列自动识别维度与指标，支持柱状图、折线图、饼图切换。
4. 明细表格：展示原始结果并支持导出，便于二次分析。

该设计兼顾“管理层看结论”和“分析人员看明细”的双层诉求。

## 5.6.7 安全控制与异常处理
为保证问数功能可控、可审计，系统实现如下机制：
1. 只读约束：仅允许 SELECT 查询，拒绝写操作类语句。
2. 敏感词拦截：对问题和 SQL 同时检测，如 `DROP`、`DELETE`、`TRUNCATE` 等。
3. 敏感表限制：禁止访问用户、权限、系统日志等管理类表。
4. 配额限制：按用户控制每日调用次数，防止滥用。
5. 异常留痕：失败请求写入错误日志，支持后台快速排障。

## 5.6.8 模块效果与应用价值
结合项目测试与运行结果，AI 问数模块取得以下效果：
1. 响应效率提升：问数全流程响应在秒级完成，满足即席分析需求。
2. 分析门槛降低：业务人员无需编写 SQL，即可完成常用分析。
3. 成本可控：标准 SQL 优先匹配策略降低模型调用频次与 token 消耗。
4. 治理能力增强：通过日志、趋势、成功率统计形成持续优化闭环。

综上，AI 智能问数模块将传统 BI 从“被动看报表”扩展为“主动问数据”，显著提升了地产企业数据服务效率与决策响应速度。

# 6.4 AI 智能问数专项测试（优化稿）

## 6.4.1 功能测试
围绕 AI 问数模块执行流程，设计以下测试项：
1. 问题输入与 SQL 生成测试：验证自然语言输入后能稳定返回 SQL。
2. 标准 SQL 命中测试：验证关键词命中后优先返回标准库 SQL。
3. 安全拦截测试：验证危险语句和敏感表访问可被拦截。
4. 配额控制测试：验证超配额后返回限制提示。
5. 历史与日志测试：验证个人历史和后台日志统计正确。
6. 可视化联动测试：验证图表渲染与图表类型切换正常。

## 6.4.2 性能测试
在典型业务问题集下，对问数模块进行分阶段计时：
1. SQL 生成阶段：平均响应时间小于 2 s。
2. 数据查询阶段：平均响应时间小于 3 s。
3. 图表渲染与解读阶段：平均响应时间小于 1.5 s。
4. 端到端总时延：整体控制在 6 s 内。

## 6.4.3 测试结论
测试结果表明，AI 问数模块在功能完整性、安全可控性和交互体验方面均达到预期目标，可满足地产企业在日常经营分析中的高频即席问数需求。后续可继续沿“领域语义增强、复杂多表推理、图表智能推荐”方向迭代优化。
