# AI数据融合平台毕业答辩 - 评委 Q&A 准备

> 本文件整理了评委可能提出的典型问题及参考答案，涵盖架构设计、技术选型、AI 问数、数据质量、系统测试等核心领域。每个问题都附带了答题要点，帮助你在答辩现场从容应对。

## 一、架构设计类问题

### Q1：为什么选择 ODS→DWD→DWS→ADS 四层架构？依据是什么？

**答题要点：**
- 参考了 Inmon 数据仓库理论和 Kimball 维度建模方法
- 四层分层是业界经典方案（阿里 OneData、百度等大厂均采用类似架构）
- **核心价值：**
  - **数据解耦**：每层职责单一，业务变化不影响底层
  - **可追溯性**：从报表指标可追溯回原始业务数据
  - **复用性**：DWS 层主题汇总可被多个 ADS 报表复用
  - **维护性**：每层可独立测试、验证和监控
- 对于本项目的数据规模（5 张业务表），四层架构体现了完整的设计思路，实际生产中可根据数据量适当合并层级

---

### Q2：为什么不在 ODS 层直接做报表查询？还要建后面的层级？

**答题要点：**
- **数据质量问题**：ODS 层数据可能存在脏数据、空值、格式不统一
- **性能问题**：直接在原始表上做多表 JOIN + 聚合，查询慢
- **口径统一**：不同报表对同一指标的计算可能不同，DWS 层统一口径
- **示例**：销售额的计算需要考虑退货、折扣等，在 DWD 层清洗后，DWS 层按日/月聚合，ADS 层直接读取，避免每次重复计算
- **类比**：如果只有一层，相当于每次查报表都要从"原料"重新加工，分层后变成了"半成品→成品"的流水线

---

### Q3：你的系统架构图中，AI 服务是通过阿里云百炼调用的，这个方案有什么优缺点？

**答题要点：**
- **优点：**
  - 无需自建 GPU 服务器，部署成本低
  - Qwen 模型对中文理解能力强，支持 SQL 生成场景
  - 阿里云百炼提供稳定的 API，SLA 有保障
  - 按需付费，适合答辩演示规模
- **缺点：**
  - 依赖外部网络，延迟受网络影响
  - 数据隐私：用户问题会传到云端
  - 无法离线使用
- **改进方向：** 可引入本地小模型（如 Qwen2.5-7B 本地部署）用于敏感场景，云端大模型作为补充

---

### Q4：系统是如何处理数据安全和用户权限的？

**答题要点：**
- **认证层面：**
  - 采用 JWT Token 机制，登录时签发 Token，后续请求携带 Token 认证
  - Token 包含过期时间（exp），过期后需重新登录
  - 路由守卫统一拦截未认证请求
- **授权层面：**
  - 基于角色的权限控制（RBAC）
  - 用户关联角色，角色关联权限
  - 后端 API 层面做权限校验，前端做按钮级显示控制
- **数据安全：**
  - API 请求使用 HTTPS（生产环境）
  - 敏感数据（密码）使用 bcrypt 加密存储
  - SQL 查询使用参数化，防止 SQL 注入

## 二、AI 智能问数类问题

### Q5：AI 问数的 80% 准确率是如何测试的？测试集怎么构建的？

**答题要点：**
- **测试方法：**
  - 构建测试问题集，覆盖简单查询、多表 JOIN、聚合、时间表达式等场景
  - 每个问题人工编写标准 SQL 作为 ground truth
  - 对比 AI 生成的 SQL 与标准 SQL 的执行结果是否一致
- **测试集分类：**
  - 简单查询（单表、无聚合）：准确率 ~95%
  - 多表 JOIN：准确率 ~75%
  - 聚合查询（GROUP BY、ORDER BY）：准确率 ~80%
  - 时间表达式（昨天、本月、上季度）：准确率 ~70%
- **综合准确率**：加权平均约 80%+
- **说明：** 准确率与问题复杂度负相关，简单问题几乎 100%，复杂 JOIN 和多条件筛选会降低

---

### Q6：AI 是怎么把自然语言转成 SQL 的？原理是什么？

**答题要点：**
- **Prompt Engineering 方案**（当前实现）：
  1. 将数据库 schema（表名、字段名、字段注释）作为 context 传入
  2. 用户自然语言问题作为 query
  3. 构造结构化的 system prompt，指导大模型生成 SQL
  4. 大模型（Qwen）基于 schema 理解和问题理解，输出 SQL
- **Prompt 示例：**
  ```
  你是一个数据分析师，根据以下数据库 schema 和用户问题生成 MySQL SQL：
  表: ods_orders(order_id, order_date, customer_id, total_amount)
  表: ods_products(product_id, product_name, category)
  ...
  用户问题: 上个月销售额最高的产品是什么？
  请直接输出 SQL，不要解释。
  ```
- **关键设计：**
  - schema 自动提取，减少手工维护
  - 提供字段注释帮助 AI 理解业务含义
  - 限制 SQL 只读，防止 DELETE/DROP 等危险操作
- **改进方向：** Text2SQL fine-tuning 可进一步提升准确率

---

### Q7：如果 AI 生成的 SQL 有误或者执行报错，系统怎么处理？

**答题要点：**
- **SQL 校验：**
  - 生成后先用 `EXPLAIN` 预检查，确认语法正确
  - 拦截危险操作（DELETE、UPDATE、DROP 等）
- **错误处理：**
  - 执行报错时，将错误信息返回给 AI，尝试修正重生成
  - 设定最大重试次数（如 3 次），避免死循环
  - 超过重试次数后，向用户展示错误信息和建议
- **用户体验：**
  - 展示生成的 SQL，让用户了解 AI 的推理过程
  - 如果结果不满意，用户可以修改问题重新查询

---

### Q8：你的 AI 问数和 ChatBI / Text2SQL 领域的主流方案比，有什么差距？

**答题要点：**
- **当前方案的局限：**
  - 基于 Prompt Engineering，依赖大模型本身的 SQL 能力，没有针对性优化
  - 没有引入 RAG（检索增强生成），无法利用历史查询做 few-shot learning
  - schema 信息一次性全量传入，表多了可能超出 context window
  - 不支持多轮对话（追问、条件追加）
- **主流方案的先进性：**
  - Spider、BIRD 等 benchmark 上的 SOTA 模型使用 fine-tuning + RAG
  - 支持 schema linking（自动识别问题涉及的表和字段）
  - 支持多轮对话和查询修正
  - 引入自校验机制（生成后验证 SQL 逻辑正确性）
- **定位：** 本系统作为毕业设计，实现了 Text2SQL 的端到端流程，验证了可行性，与工业级方案在工程化、准确率上有差距，但作为学术探索是完整的

## 三、技术选型类问题

### Q9：为什么选择 FastAPI 而不是 Spring Boot 或 Django？

**答题要点：**
- **FastAPI 的优势：**
  - Python 生态，与数据科学、AI 领域天然契合
  - 异步性能优异（基于 Starlette + uvicorn），实测 QPS 远超传统框架
  - 自动生成 OpenAPI/Swagger 文档，开发调试效率高
  - 类型校验基于 Pydantic，减少手动参数校验代码
- **Spring Boot：** Java 生态，适合大型企业级项目，但对 AI/数据科学集成不如 Python 友好
- **Django：** 功能全面但较重，对于本项目以 API 为主的场景，FastAPI 更轻量灵活

---

### Q10：前端为什么选 Vue3 + Element Plus？为什么不用 React？

**答题要点：**
- **Vue3 的优势：**
  - 组合式 API（Composition API）代码组织更清晰
  - 学习曲线平缓，开发效率高
  - 响应式系统基于 Proxy，性能优于 Vue2
- **Element Plus：** 企业级组件库，开箱即用，适合后台管理系统
- **React 也可以：** 但 Vue3 + Element Plus 在国内企业应用广泛，生态成熟，组件更贴合国内后台管理需求
- **对于本项目：** 核心诉求是快速搭建功能完整的后台界面，Vue3 方案效率更高

---

### Q11：为什么集成 Metabase 而不是完全自研 BI？

**答题要点：**
- **定位互补：**
  - 自研前端：固定报表 + AI 问数，满足标准化需求
  - Metabase：灵活自助分析，满足探索性分析需求
- **开发成本：** 完全自研一个功能齐全的 BI（拖拽图表、数据源管理、权限等）工作量巨大
- **技术验证：** Metabase 作为成熟开源 BI，验证了"自研 + 开源集成"的混合方案可行性
- **学习价值：** 展示了系统集成能力，也是企业常见的技术选型策略

---

### Q12：为什么用 Docker Compose 而不是 Kubernetes？

**答题要点：**
- **项目规模：** 本项目只有 4-5 个服务容器，Docker Compose 完全够用
- **Kubernetes 过重：** K8s 适合微服务架构（10+ 服务）、需要自动扩缩容、高可用的场景
- **答辩演示场景：** Docker Compose 一键启动，简单可靠
- **扩展性：** 如果未来接入更多服务，可以从 Docker Compose 平滑迁移到 K8s

## 四、数据质量类问题

### Q13：ETL 过程中如果数据源发生变化（如新增字段），系统怎么处理？

**答题要点：**
- **当前方案：**
  - ETL 脚本基于固定的表结构映射
  - 如果业务表新增字段，需要同步修改 ETL 映射配置
- **改进方向：**
  - 引入 schema 自动发现机制，定期比对源表和目标表结构差异
  - 新增字段自动在 ODS 层创建，并标记为待处理
  - 提供配置化的字段映射界面，无需修改代码
- **实际生产中的方案：** 使用 CDC（Change Data Capture）如 Debezium 捕获 schema 变更

---

### Q14：数据同步是全量还是增量？增量同步怎么实现的？

**答题要点：**
- **首次同步：** 全量同步，将业务库数据全部导入 ODS 层
- **后续同步：** 增量同步，基于 `updated_at` 时间戳字段
  - 记录上次同步的最大 `updated_at` 时间
  - 下次同步时只拉取 `updated_at > last_sync_time` 的数据
- **局限：**
  - 依赖业务表有 `updated_at` 字段
  - 不支持物理删除的同步（业务库删除的数据，ODS 层不会删除）
- **改进方向：** 使用 Binlog CDC 方案，可捕获 INSERT/UPDATE/DELETE 全量变更

---

### Q15：如何保证各层数据的一致性？

**答题要点：**
- **数据校验：**
  - 每层 ETL 完成后，执行数据量校验（ODS 数量 ≤ 业务库，DWD ≤ ODS 等）
  - 关键字段非空校验
- **事务保证：**
  - 每层 ETL 在一个数据库事务中执行，失败回滚
  - 使用事务日志记录 ETL 执行状态
- **对账机制：**
  - 定期执行 ADS 层指标与业务库原始数据对账
  - 差异超过阈值时告警
- **当前实现：** ETL 脚本中有基础的行数统计和日志记录

## 五、系统测试类问题

### Q16：你的系统测试是怎么做的？测试覆盖率 85% 怎么来的？

**答题要点：**
- **测试类型：**
  - 单元测试：测试独立函数和模块（如 ETL 清洗函数、权限校验）
  - 集成测试：测试 API 端到端响应（请求 → 处理 → 响应）
  - 性能测试：页面加载时间、API 响应时间
- **覆盖率计算：**
  - 使用 Python 的 `coverage` 工具统计代码行覆盖率
  - 85% 表示 85% 的代码行在测试中被执行过
  - 剩余 15% 主要是异常分支、日志代码等
- **说明：** 覆盖率高不代表测试质量高，核心是覆盖了关键业务路径

---

### Q17：压力测试 100+ 并发用户是怎么测的？

**答题要点：**
- 使用工具（如 Apache JMeter / locust / ab）模拟并发请求
- 针对核心 API（如 `/api/dashboard`、`/api/reports/sales/kpi-summary`）发送并发请求
- 观察指标：响应时间、错误率、吞吐量
- 在 Docker 环境下，100 并发用户响应时间 < 2 秒，无错误请求
- **说明：** 这是单机测试，未考虑多实例负载均衡的情况

## 六、创新与价值类问题

### Q18：你的系统和市面上的 BI 工具（如 Tableau、Power BI）比，有什么优势？

**答题要点：**
- **功能定位不同：** 它们面向专业分析师，本系统面向业务人员
- **AI 问数是差异化：** Tableau/Power BI 的自然语言查询能力较弱或需要付费
- **成本低：** 完全开源方案，无软件许可费用
- **定制化：** 可以针对特定业务场景深度定制
- **学习价值：** 展示了从底层数据管道到上层可视化的全链路能力
- **客观承认差距：** 在图表丰富度、交互体验、生态集成上，与商业 BI 工具仍有较大差距

**答题要点：**

  - 显著降低了数据分析的使用门槛

- **其他亮点：**

### Q20：这个项目能应用到实际生产环境吗？还需要做哪些改进？

**答题要点：**
- **当前可直接使用的：**
  - 数仓分层架构和 ETL 流程

- **需要改进的：**
  - **高可用**：需要多实例部署 + 负载均衡 + 数据库主从

  - **调度**：ETL 需要接入 Airflow/DolphinScheduler 等专业调度工具

## 答题技巧

1. **先肯定问题价值**："这个问题很好/很关键"
2. **分点回答**：用"第一、第二、第三"的结构，让评委听得清楚
3. **承认不足**：对于确实没做到的，坦诚说明现状和改进方向
4. **用数据说话**："准确率 80%""响应 < 3 秒""24 张表"等具体数字
5. **不要硬刚**：遇到不懂的，可以说"这个方向我研究不够深入，后续会补充学习"
6. **控制时间**：每个问题回答 1-2 分钟，避免展开过深
